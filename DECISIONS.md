# DECISIONS.md

Decision records. One entry per decision below the index; an entry is never deleted: when a decision
changes, the old entry is marked "Superseded by D-xxx" and a new entry is added (or, for an entry
still under review, it is updated in place and the change is noted in it).

Status values: **Accepted**; **Proposed** (recorded on a task branch, pending review before the
branch is published); **Superseded by D-xxx**.

Dates are the date of the commit that recorded the decision (D-022 to D-027 previously carried
2026-10-17 / 2026-10-18, later than the commits that added them on 2026-10-16). Entries D-028 to
D-036 were backfilled on 2026-10-17 from docs/QUESTIONS.md items that were published through a
reviewed pull request. "Context: not recorded" means the repository does not show why.

## D-001 OpenFOAM ESI v2606 only
- Status: Accepted
- Context: docs/PLAN.md listed the OpenFOAM flavour (ESI vs Foundation) as an open decision blocking Phase 1.
- Decision: support OpenFOAM ESI v2606 only, installed at /usr/lib/openfoam/openfoam2606.
- Alternatives considered: OpenFOAM Foundation (openfoam.org); supporting several versions through an adapter layer (PLAN 1.2).
- Consequences: no flavour adapter is needed; keywords follow the v2606 tutorials.

## D-002 Run inside WSL2 with WSLg
- Status: Accepted
- Context: OpenFOAM is Linux software and the owner works on Windows 11.
- Decision: the whole application runs in WSL2 Ubuntu 24.04 and displays through WSLg.
- Alternatives considered: not recorded (a Windows GUI driving a Linux solver across file systems is implied by the reason).
- Consequences: no cross-OS path translation; rendering relies on Mesa d3d12 (see the GPU debt in docs/STATUS.md).

## D-003 Three-layer package structure
- Status: Accepted
- Context: simulation logic must run headless (tests, scripts) without Qt.
- Decision: core/, foam/ and gui/ layers; core and foam never import Qt, pyvista or vortexcfd.gui (tests/test_layers.py). Extended by D-018 and D-031.
- Alternatives considered: not recorded.
- Consequences: headless pipeline tests; GUI-free automation is possible.

## D-004 OpenFOAM always launched through explicit sourcing
- Status: Accepted
- Context: OpenFOAM is not on PATH and the user's shell environment varies.
- Decision: every OpenFOAM process goes through vortexcfd.foam.runner, which sources /usr/lib/openfoam/openfoam2606/etc/bashrc.
- Alternatives considered: not recorded.
- Consequences: deterministic execution independent of the user's shell.

## D-005 Results stored as standard OpenFOAM cases
- Status: Accepted
- Context: Task 0.6 (ParaView decision).
- Decision: no application-specific result format; every case can be opened in ParaView.
- Alternatives considered: not recorded.
- Consequences: the in-app viewer is a convenience; an "Open in ParaView" button is planned for Phase 6.

## D-006 Project file: JSON, pydantic, schema_version

- Consequences: human-readable files; migrations in core/project_io.py (D-020, schema v3 in Task 4A).

## D-022 External-aerodynamics BCs and motorBike numerics
- Status: Accepted (reviewed 2026-10-17 in the review chat; was Proposed on task/4a-physics, docs/QUESTIONS.md item 37)
- Context: Task 4A, steady incompressible kOmegaSST.
- Decision: inlet fixedValue U/k/omega, p zeroGradient; outlet p fixedValue 0, U/k/omega inletOutlet; sides/top/bottom slip (nut calculated, as the motorBike tutorial); symmetry symmetryPlane; part walls noSlip, kqRWallFunction, omegaWallFunction, nutUSpaldingWallFunction. Schemes and solution settings: motorBike tutorial (preset "robust").
- Alternatives considered: the tutorial's nutkWallFunction (not valid down to y+ about 1).
- Consequences: behaves like a known-good tutorial case. The k wall BC sensitivity is studied in docs/validation/flat_plate/README.md.

## D-023 Inlet turbulence from intensity and viscosity ratio
- Status: Accepted (reviewed 2026-10-17 in the review chat)
- Context: Task 4A.
- Decision: k = 1.5 (V I)^2, omega = k / (nu ratio).
- Alternatives considered: raw k and omega (the motorBike tutorial's fixed values).
- Consequences: the user enters the two numbers an engineer knows.

## D-024 y+ estimator and absolute layer sizing
- Status: Accepted (reviewed 2026-10-17 in the review chat)
- Context: Task 4A.
- Decision: first cell height from Cf = 0.026 / Re^(1/7) (y = y+ nu / u*); with layer_sizing "absolute_yplus" snappyHexMesh uses relativeSizes false with that firstLayerThickness and the reused expansion ratio.
- Alternatives considered: not recorded.
- Consequences: measured y+ on the flat plate is within 6 % of the estimate (docs/validation/flat_plate/README.md). Guidance (added 2026-10-17): the flat-plate verification gives Cf about 6 % low at y+ 1 and about 3.6 % low at y+ 0.5 against the TMR SST reference (docs/validation/flat_plate); the Mesh properties show this as a muted note under Target y+ when the layer sizing is absolute y+.

## D-025 Validation marker and policy
- Status: Accepted (confirmed by D-043)
- Context: validation runs real OpenFOAM cases and takes minutes.
- Decision: validation tests carry the `validation` marker, are skipped unless selected with `-m validation`, are excluded from scripts/ship.sh and are run explicitly after every change to physics or numerics; results live in docs/validation/.
- Alternatives considered: running them as a merge gate (too slow and sensitive).
- Consequences: a numerics change must be accompanied by a validation run.

## D-026 Layer count from the y+ first layer
- Status: Accepted (layer count confirmed by D-042). The minTetQuality part is superseded by D-044.
- Context: Task 4A; thin y+ layers on coarse surfaces collapse.
- Decision: with absolute y+ sizing, n = ceil(ln(0.5 h / t1) / ln r) + 1 clamped to [1, 30] (t1 first layer, r expansion, h surface cell size); the Mesh panel and Generate Mesh warn when 30 layers do not reach 0.5 h. For this sizing minTetQuality is set to -1e30.
- Alternatives considered: a user-entered layer count.
- Consequences: layers blend into the volume cells without the user counting them.

## D-027 Residual targets as SIMPLE residualControl

## D-028 Part patch names
- Status: Accepted (published in PR #11; from docs/QUESTIONS.md items 2 and 20)
- Context: OpenFOAM patch names must be valid words and unique.
- Decision: a part's patch is its name with every character outside [A-Za-z0-9_] replaced by `_` (case kept); a collision with a domain boundary name (inlet, outlet, sides, top, bottom, symmetry) or another part gets the first free numeric suffix (`_1`, `_2`, ...). The tree shows the original part name; the Part properties show the patch name read-only.
- Alternatives considered: not recorded.
- Consequences: patch names are stable and never clash with the far-field patches.

## D-030 snappyHexMesh case conventions
- Status: Accepted (published in PR #11; items 7 to 11)
- Context: Task 5.1.
- Decision:
  - checkMesh runs without -allGeometry -allTopology; the report keeps cells, faces, points, max/avg non-orthogonality, max skewness and the failed-check count; a mesh with failed checks is still shown, as a warning.
  - surfaceFeatureExtract on every part STL with includedAngle = 180 - feature_angle; feature level = surface_level_max; resolveFeatureAngle = feature_angle.
  - locationInMesh upstream of the parts' box, midway to the inlet, at cell fractions (0.34, 0.41, 0.28) of the background cell (at least 0.027 of a cell from every face up to level 4).
  - one nSurfaceLayers entry per part (regex "<part>.*"); layers = 0 switches the layer step off (addLayers no).
  - Generate Mesh requires every part file to exist.
- Alternatives considered: not recorded.
- Consequences: deterministic dictionaries from the project.

## D-031 foam/ and geometry/ do not import each other
- Status: Accepted (published in PR #11; item 15)
- Context: foam/ must not depend on pyvista; geometry/ must not depend on OpenFOAM.
- Decision: estimate_mesh takes the domain bounds and L as plain data; orchestration joining core, geometry and foam lives in gui/meshing.py (Qt-free); tests/test_layers.py forbids foam -> geometry and geometry -> foam.
- Alternatives considered: passing a DomainBox into foam/ (would import geometry/).
- Consequences: both layers stay usable on their own.

## D-032 Layer coverage metric and warning
- Status: Accepted (published in PR #11 and PR #12; items 18 and 32)
- Context: snappyHexMesh prints no per-patch count of faces that received layers.
- Decision: per patch, both the average layers present / target (snappy's "mesh" column) and the achieved thickness percentage are shown ("2.1 / 3 (70 %), thickness 64 %"); either below 80 % warns (colour and console WARNING). The overall share of extruded faces (last "Extruding N out of M faces") is shown separately.
- Alternatives considered: thickness percentage alone (item 18, refined by item 32).
- Consequences: a partly collapsed layer stack is visible in the Mesh properties.

## D-033 Mesh staleness and persistence
- Status: Accepted (published in PR #11; item 19, superseding item 6)
- Context: Task 5.1.
- Decision: a "Mesh out of date" badge (next to Saved/Modified), a Status row in the Mesh properties and a VTK text in the Mesh Scene. The hash covers part names, units, part file contents, the domain and the mesh settings (not the project name, view settings or coverage threshold). The last report is stored in case/vortexcfd_mesh.json and shown when the project is opened, even if case/polyMesh was deleted.
- Alternatives considered: not reloading meshes at open (item 6, the earlier behaviour).
- Consequences: the user always sees whether the mesh matches the inputs.

## D-034 Properties panel and column defaults
- Status: Accepted (published in PR #11 and PR #12; items 22 to 24, 30 and 31). Whether the left column should default to 20u is still open (docs/QUESTIONS.md item 30).
- Context: readability of the properties at fonts 11 to 18.
- Decision: left column starts at 18u (min 14u, max 28u); tree / properties split 40 % / 60 % (user drag stored in QSettings layout/left_tree_fraction); monitors column 25 % of the window so the viewer keeps at least 50 %; property rows go side by side when the panel is at least 20u wide (label column clamped to [8u, 50 %], field at least 7u), otherwise they stack; domain size text uses three significant digits.
- Alternatives considered: the mockup's measured proportions (tree split 0.548, monitors 34.7 %).
- Consequences: at the default 18u the rows are stacked.

## D-035 Mesh Scene section plane
- Status: Accepted (published in PR #12; items 27 to 29, 33 and 34)
- Context: Task 5.1 follow-up (section plane through the volume mesh).
- Decision: cut cells in mesh_edge over mesh_surface; framing = parts' box plus 0.3 part extents; the camera looks from the plane's negative side and part walls are clipped behind the plane; default plane normal +y through the centre of the part patches (with symmetry: the symmetry plane nudged 0.2 % of the domain inside); changing the normal resets the offset; controls in their own strip under the scene tabs (Mesh Scene only); domain boundary patches translucent in border_active, off by default; slider re-slices at most every 150 ms while dragging and once on release.
- Alternatives considered: part_edge over elevated (item 26: low contrast).
- Consequences: prism layers are visible as bands at the default zoom on a 1 m sphere.

## D-036 Flat plate validation cases and criterion
- Status: Accepted (updated 2026-10-17: reference changed from White's law to the NASA TMR SST results, decided in the review chat; docs/QUESTIONS.md items 39 and 40)
- Context: PLAN validation policy: turbulence setup logic is validated on a flat plate (Cf, y+). The first Case B failed a 5 % criterion against White's law (Cf(0.97) = 2.556e-3, -11 %). The TMR SST page shows the case is a VERIFICATION case and that verified codes are themselves 5-7 % below White's law at x = 0.97, so White is not a valid pass/fail reference for SST. docs/validation/flat_plate/README.md.
- Decision: Case A (U = 10 m/s, Re_L = 1.3e6) is informative only. Case B (TMR 2D zero pressure gradient flat plate, Re = 5e6 per metre, plate 0 to 2 m) is the arbiter: a wall-normal grid study on three nested grids (first-cell y+ about 1, 0.5, 0.25, at least 30 cells across the boundary layer), Cf(x = 0.97) extrapolated with the Celik GCI procedure, compared with the TMR incompressible SST reference (2.7214e-3, tests/data/tmr/). Bands: |error| <= 3 % PASS; 3-5 % PASS WITH NOTE (citing the TMR note on OpenFOAM's SST implementation); > 5 % FAIL. The validation test asserts the recorded band (a strict xfail only for FAIL). White's law and the TMR Cf(x) distribution are informative. The y+ estimator must be within 30 % at mid-plate. Split in two: the full study (three grids, GCI, TMR distribution, optional k wall BC diagnostic) is `scripts/validation/flat_plate_study.py` (about 80 min, 2 h with --k-wall; writes the Case B files and the README tables, committed); the pytest `validation` test runs Case A and the coarse and medium grids only (about 20 min) and asserts the medium grid within 5 % of the reference, a decreasing error from coarse to medium, reproduction of the committed study within 0.1 %, and the recorded verdict band with the committed finest grid.
- Alternatives considered: White's law 0.455 / ln^2(0.06 Re_x) with mean <= 5 % / max <= 8 % (the first criterion); the power law 0.0592 Re_x^-0.2.
- Consequences: result of 2026-10-17: extrapolated Cf(0.97) = 2.6314e-3 (GCI 0.035 %), -3.31 %: PASS WITH NOTE. After a numerics change the full study must be re-run and its results committed, or the pytest reproduction check fails.

## D-046 Running the solver: run states, run record, results staleness
- Status: Accepted (reviewed 2026-10-17 in the review chat; recorded as Proposed on task/4a-physics). The old results left by Generate Mesh are now deleted by D-051.
- Context: Task 4B.1 runs simpleFoam from the GUI on the meshed case.
- Decision:
  - Run Solver is enabled when the project is saved, no meshing is running, a mesh exists (case/vortexcfd_mesh.json loaded), the mesh is not out of date (D-033) and the physics is valid; otherwise it is disabled with the reason as tooltip ("Save the project first.", "Meshing is running.", "Generate the mesh first.", "The mesh is out of date: generate it again.", or the physics problem). "Physics valid" means: the Simulation validates again (a project edited outside the Project API) and the forceCoeffs reference length and area are positive (a flat part with no y extent has a zero bounding-box area). While running the state badge shows "Solving".
  - case/vortexcfd_run.json keeps the state, iterations, the last initial residual of every solved field, the exit code and a results hash: the mesh inputs hash (D-033) plus the physics, inflow, solver and report settings. ## D-052 Lost-part guard, thin-part warning, per-part levels and seed lines (schema v5)
- Status: Accepted (review chat 2026-10-17, [NUMERICS-REVIEW]; updated in that review: seeding is automatic, docs/QUESTIONS.md items 54 and 55). The manual-only seeding first recorded here (seed lines only for parts with a level override) is superseded by the automatic seeding below. Where the seed lines go in snappyHexMeshDict (`features` of the single run) is superseded by D-084 (a castellation-only run; never snap features).
- Context: a sphere (radius 0.5 m) plus a flattened ellipsoid (0.6 x 0.4 x 0.4 m) 1.5 m downstream, default sizing, gave a mesh with no patch for the ellipsoid while checkMesh said "Mesh OK"; a solver run would give credible but wrong forces. Root cause (reproduced, logs in the Part A report): snappyHexMesh finds a surface only where the segment between two neighbouring cell centres crosses it (its "Number of edges" equals the number of faces). The two-part domain gives a 0.596 m background cell, so near the ellipsoid those segments run at y, z = +-0.30 m while the ellipsoid spans only +-0.20 m: no segment crosses it, it is never marked for refinement (raising its surface level to 5-6 or 6-7 changed nothing), its interior is never separated from the flow region, and snapping has no faces for its patch. Shifting it off the grid planes, flipping its normals or a distance-mode refinementRegion (shell refinement runs only after surface refinement) did not help either; a finer background (0.375 m) gave only 16 faces.
- Decision:
  - Guard: after every mesh, constant/polyMesh/boundary is read; a part patch that is missing or has 0 faces is a lost part. MeshReport gains `lost_parts` and `valid` (checkMesh OK and no lost part); the summary adds "Part <name> was lost during meshing", logged as an ERROR, shown in the error colour in the Mesh properties (Lost parts row) and in the top-bar mesh badge ("Mesh invalid: Part <name> lost"), and Run Solver is disabled with that reason. The mesh record keeps lost_parts (absent in older records = none).
  - Pre-mesh criterion (foam/mesh_case.needs_seeding): a part whose second-largest bounding-box extent is below sqrt(2) background cells (a convex part is certain to be crossed by the lattice of cell-centre lines only if its largest projection holds a disc of sqrt(2) cells), or that is thinner than 3 surface cells at its maximum level. Such a part is noted in the Mesh properties, the Generate Mesh tooltip (the button stays enabled) and the console when meshing starts: "Part <name> is small relative to the background mesh: refinement seeded automatically".
  - Per-part refinement: Part gains optional surface_level_min / surface_level_max (None = the Mesh levels; only the max set gives min = max - 1; shown as "auto" in the Part properties); its refinementSurfaces entry and its feature level use them; they are meshing inputs (mesh hash). Schema v5 with migration (hand-written v4 fixture).
  - Seed lines, automatic: every part flagged by the criterion gets constant/triSurface/<part>_seed.eMesh, three axis-aligned lines through the centre of its bounding box reaching 20 % beyond it, added to `features` at the part's maximum level (its overrides if set, otherwise the mesh's computed levels), without user action. Explicit feature refinement runs before surface refinement and needs no intersection, so the cells along the lines are refined and the surface is then found. The reproduced case with DEFAULT settings: 135265 cells, Ball 1952 faces, Pod 1304 faces, checkMesh Mesh OK, the guard passes (before seeding: 120709 cells, Pod lost). The lost-part guard stays for any other cause.
- Alternatives considered: raising the part's surface level only (no effect, see Context); a distance-mode refinementRegion around the part (applied after surface refinement: 40 faces); a finer background everywhere (costly, 16 faces at 0.375 m); seeding only parts with a level override (the first version of this entry, superseded in the review).
- Consequences: a lost part can no longer reach the solver; the user is warned before meshing and fixes it with the part's levels. Seed lines add a thin column of refined cells inside the part (removed with the part interior). Test bound: the real meshing tests that build their own mesh (tests/test_lost_parts.py, tests/test_force_projection.py) allow 240 s per OpenFOAM step and 600 s in total instead of the 120 s of D-043, because under `-n 8` they run next to every worker's session sphere mesh and timed out once.

## D-058 Stopping criteria: runTimeControl for residuals, app-side range-based asymptotic criterion, convergence banner (schema v6)
- Status: Accepted (review chat 2026-10-17, [NUMERICS-REVIEW], docs/QUESTIONS.md items 60 and 62). Revised in place on 2026-10-18 after the review: the asymptotic criterion is range-based and evaluated by the app (it was runTimeControl's `average` condition, |x_n - mean of the last W| <= an absolute tolerance), and the end state is "Criteria met" (it was "Converged").
- Context: the only stop besides the iteration limit was the SIMPLE residualControl (D-027). The owner's principle is that a run must be judged by more than the final coefficients; the app needs stopping criteria on residuals and on monitored quantities, a clear statement of what stopped a run, and every stop must be a clean end that writes the last iteration (never a kill). The first version used runTimeControl's `average` condition for asymptotic criteria; it is met by chance when a drifting series crosses its window mean (it stopped the coarse sphere at iteration 49 while Cd still drifted by several per cent).
- Decision:
  - Model (schema v6, extended in place on the unpublished branch): `Solvers.stopping` = `StoppingCriteria`: a list of criteria, `combine` "all" (default) or "any", `min_iterations` (default 0) before which no criterion may stop the run, and the oscillation settings of D-059. The iteration limit is `Solvers.iterations` (always present). Criterion kinds: `residual` (field p, U, k or omega; threshold on the initial residual) and `asymptotic` (a quantity of D-060; `window` W, default 50 iterations; `tolerance`, relative, default 1e-3; `floor`, None = the quantity's default: 0.01 for force and moment coefficients (core/reports.default_floor); a probe quantity has no default and the model rejects it without a floor; the GUI suggests 1 % of the free-stream dynamic pressure 0.5 U^2 for p or of the speed for U when the quantity is chosen, and resets the floor whenever the quantity changes, since it is in the quantity's units). The v5 residual targets (`Solvers.residual_p/u/k/omega`) are removed; migration v5 -> v6 turns them into four residual criteria combined with "all" (a target the file did not set takes its old default), which is the same stop as the residualControl they fed; new projects get the same four criteria (hand-written fixture tests/data/project_v5.json).
  - Asymptotic criterion: over the last W iterations (one value per iteration; writeAndEnd's repeated last row counts once), r = (max - min) / max(|mean|, floor) <= tolerance. For a vector (a probe's U) max - min is the length of the vector of per-component ranges and |mean| the length of the mean vector. It is evaluated only once W values exist and from `min_iterations` on (earliest iteration max(min_iterations, W)).
  - Native / app-side split (OpenFOAM v2606 has no range-based condition):
    - only residual criteria: a `runTimeControl` function object (`runTimeControl1`, libs utilityFunctionObjects, satisfiedAction end) placed last in controlDict, one `equationInitialResidual` condition per criterion (fields (<field>), value, mode minimum, timeStart = min_iterations): met when the initial residual of the field's first solve in the iteration (U: the largest component) is below the threshold; v2606 never checks it before time index 3. "all" puts every condition in groupID 1 (all met in the same iteration), "any" gives each its own group. Keywords read from the v2606 sources (src/functionObjects/utilities/runTimeControl) and checked by a test. On a stop runTimeControl calls writeAndEnd (the iteration is written, End, exit code 0). This is the path the flat plate validation exercises.
    - at least one asymptotic criterion: no runTimeControl is written. `SolverRun` (foam/solver_run.py) evaluates ALL criteria after every iteration from the live data with the same code as the monitors panel (foam/convergence.evaluate: residuals from LogParser, quantities from the postProcessing files through ReportMonitor, rows after the iteration ignored) and combines them with "all" (every criterion met at that iteration) or "any" (`criteria_met`). When they are met it stops the solver with the existing clean stop (SIGUSR1 and stopAtWriteNowSignal, D-010). Timing, measured and read in the v2606 sources: the function objects of iteration n run after its ExecutionTime line (Time::run at the start of the next loop), so iteration n is checked on the next line `Time = n+1` (or End); that line is printed after the time increment, and v2606 applies the stop signal at the next increment (Time::operator++, stopAt writeNow sets endTime to the new time), so the solver runs and writes iteration n + 2, then prints End with exit code 0.
  - End state and record: a new state `criteria_met`, label "Criteria met: <criterion names>" (convergence.short_label, e.g. "Criteria met: Cd asymptotic"), replaces "Converged". It is set when runTimeControl printed "<type>: <name> condition satisfied" and "Stopping calculation" (LogParser event `CriteriaMet`), when the app's evaluation stopped the run (and the user did not stop it as well), and for old logs ending with "SIMPLE solution converged". The run record (case/vortexcfd_run.json) gains `met_labels` and `met_iteration` (the iteration at which the criteria were met; the record's `iterations` is the last written one) next to `criteria` and `stopped_by` (exact descriptions, e.g. "Cd: (max - min) / max(|mean|, 0.01) over the last 20 <= 0.02"). Records saved with state "converged" are read as `criteria_met` and written back (foam/run_record.OLD_STATES).
  - residualControl is not written in fvSolution: it would end the run on its own targets, ignoring min_iterations and "any".
  - GUI: a "Stopping Criteria" node under Solvers: Combine criteria, Minimum iterations, Maximum iterations (= Solvers.iterations), oscillation threshold (%) and window, "Add residual" / "Add asymptotic", and per criterion its settings (an asymptotic criterion: Quantity, Window, Tolerance, Scale floor), a Remove button and its earliest stop iteration; every edit commits through the Project (one undo step) and a rejected value is reverted with a message. The monitors column shows, only when criteria exist, a convergence banner and a table (criterion, current value, threshold, satisfied yes/no) evaluated live with the same code. Banner texts: "Criteria met at iteration N: <criteria that stopped it>" (success colour; N is the iteration at which they were met), "Iteration limit reached without meeting the criteria" (warning), "Stopped by the user before the criteria were met" (warning), "The solver crashed before the criteria were met" (error), "Solving: stopping criteria not met yet" while running, "No solver run yet". The status message says "Solver: Criteria met: <names> after <last iteration> iterations (<descriptions> at iteration N)".
- Alternatives considered: runTimeControl's `average` condition (the first version; absolute and met by chance at a crossing of the mean); a chained `valueAverage` function object under an `average` condition (tests the drift of the windowed mean, still absolute); rewriting controlDict during the run with a relative tolerance (fragile); a `coded` function object implementing max - min (compiles at run time, a compiler dependency); the app evaluating residual criteria as well (the native stop is validated by the flat plate and needs no signal); writing endTime = n + 1 in controlDict instead of the signal (runTimeModifiable re-reads on the file's modification time; the signal is the tested clean stop).
- Consequences: on the stop_run fixture (the old stop at iteration 49, Cd window 20) the range is 29.8 % at iteration 49 and the new criterion does not stop with window 20 and tolerance 1e-3; on the 300-iteration continuation of the same set-up (tests/data/breakdown_run) the defaults (window 50, tolerance 1e-3) never stop (Cd still spans 1.46 % of its mean over iterations 251-300); window 50 tolerance 1e-2 would stop at 245, window 20 tolerance 2e-2 at 144. Real run (slow test, fixture tests/data/asymptotic_stop_run): Cd, window 20, tolerance 2e-2, limit 250: met at iteration 144 (Cd 0.16856-0.17194 over iterations 125-144, mean 0.17087, range 1.97 %; 2.35 % at 143), the app stopped simpleFoam cleanly, iteration 146 written with U and p, End, exit code 0. Synthetic checks: a linear drift never stops, a damped oscillation stops only once its swing over the window is below the tolerance, a constant stops at the first eligible iteration. A probe criterion with a loose tolerance (window 6) is met at 6 and the run ends at 8. With a mixed residual/asymptotic set the residual criteria are evaluated by the app too, with the same rule as equationInitialResidual (the first solve's initial residual, U its largest component, not before iteration max(3, min_iterations)). Changing the criteria changes the results hash (they are solver settings). Older projects open with the same stop they had: the flat plate validation (`-m validation`, residual criteria 1e-5 on p, U, k, omega with "all", native runTimeControl) stops at exactly the iterations recorded with residualControl (Case A 494, Case B 881 and 3395) and gives the same Cf and verdict (PASS WITH NOTE).

## D-059 Oscillation warning for monitored quantities
- Status: Accepted (review chat 2026-10-17, [NUMERICS-REVIEW], docs/QUESTIONS.md item 61). Revised in place on 2026-10-18: the amplitude uses the asymptotic criterion's normalisation (it was (max - min) / |mean|, not evaluated when |mean| < 1e-3).
- Context: a steady RANS run of a flow that is physically unsteady never settles; the coefficients swing and the final values depend on where the run stops. The user must be told.
- Decision: for each monitored quantity (the asymptotic criteria's quantities and the report slots' assignments; y+, mass imbalance and x_cp are left out), over the last W = `StoppingCriteria.oscillation_window` iterations (default 100; one value per iteration): mean m, amplitude a = (max - min) / max(|m|, floor), with the floor of the asymptotic criterion watching that quantity, else the quantity's default (0.01 for force and moment coefficients, D-058). A quantity without a floor (a probe in a slot without a criterion) keeps the old rule: not evaluated when |m| < 1e-3, else a = (max - min) / |m|. Not drifting: the least-squares straight line through the W values changes by less than 0.5 * (max - min) across the window. The warning is shown in the warning colour under the convergence banner when a > `oscillation_threshold` (default 0.01, i.e. 1 %, editable on the Stopping Criteria node as a percentage) and the mean is not drifting: "<quantity> oscillates by <a>% - the flow may be unsteady; a steady solution may not exist" when |m| >= floor, and "<quantity> oscillates with a range of <max - min> around a mean near zero (<m>) - ..." when the floor governs. Not evaluated with fewer than W values. It is a warning only, never a stop.
- Alternatives considered: a spectral test (FFT peak; needs many periods and more code for the same message); standard deviation instead of max - min (less direct to state).
- Consequences: on the real 172-iteration coarse-sphere run (tests/data/oscillation_run) iterations 73-172 give Cl 0.038-0.092 around 0.061 (88 %) and Cd 0.161-0.180 around 0.169 (11 %): both flagged as before. CmPitch (mean 2.4e-4, range 1.23e-4), not evaluated before, is now judged against the 0.01 floor: 1.2 %, just above the 1 % default threshold, so it is flagged too when it is monitored. Synthetic: Cl = 0 +- 4e-5 (0.8 % of the floor) is not flagged; Cl = 0 +- 0.05 is.

## D-060 Force breakdown, centre of pressure, mass balance and probes as reports
- Status: Accepted (review chat 2026-10-17, [NUMERICS-REVIEW], docs/QUESTIONS.md items 63 and 64). Revised in place on 2026-10-18: x_cp in the body axes with a 1e-3 threshold (it was "global axes", threshold 0.01), probes interpolated with cellPoint (they were cell values), asymptotic criteria app-side (D-058).
- Context: Cd and Cl alone do not validate a result; the user needs to see where the force comes from (pressure or friction, which part), whether mass is conserved, and point values in the flow.
- Decision:
  - Function objects added to controlDict (keywords checked by tests against the v2606 sources): with two or more parts, per part `forceCoeffs_<patch>` and `forces_<patch>` (same settings as forceCoeffs1 / forces1 on that patch only; with one part they would equal the totals and are not written); `massFlow_inlet` and `massFlow_outlet` (surfaceFieldValue, regionType patch, operation sum, fields (phi), every iteration; the far-field patches are slip and the symmetry plane is symmetryPlane, so their flux is zero by construction and they are not summed); one `probe_<name>` probes object per probe (fields (p U), one probeLocations point, `interpolationScheme cellPoint` (probeModel.C reads it; interpolationCellPoint's TypeName; the default "cell" would give the containing cell's value), sampleOnExecute).

Checked on real runs: the projection equals forceCoeffs' Cd, Cl and CmPitch to 1e-7 for all walls and for each part, and the parts add up to all walls.
  - Centre of pressure in the body axes: the point on the line through CofR parallel to the body x axis where the resultant gives the same pitching moment, x_cp = x_ref - M_y / F_z(body), x_ref = x of CofR. The app turns the free stream by the angle of attack and never the body, so the body axes are the geometry's axes (x along the chord, z normal to it) and F_z(body) is the global z force whatever the incidence (not the lift, which is normal to the free stream). Undefined (shown "undefined", not plotted) when |F_z(body)| < 1e-3 q A_ref (foam/forces.CP_MIN_NORMAL), stated in the Forces table tooltips.

Above 0.1 % in magnitude it is shown in the warning colour on the Reports & Monitors node and as a warning under the convergence banner ("Mass imbalance X% of the inlet flux (above 0.1%): the continuity solution is not converged").
  - Report ids (core/reports.py) replace the fixed list of D-048: Cd, Cl, CmPitch; Cd_pressure, Cd_viscous, Cl_pressure, Cl_viscous, x_cp; the same per part as `<base>@<patch>` (offered only with several parts); mass_imbalance; yplus_min/avg/max; `probe:<name>:<p|Ux|Uy|Uz|Umag>`. The slot menus group them in submenus (All walls, Part <patch>, Probe <name>). An id whose part or probe was removed stays assigned and is marked "(not available)".
  - Asymptotic criteria (D-058) may watch any force coefficient of all walls or of one part (Cd, Cl, CmPitch and the pressure and viscous parts) and `probe:<name>:p` or `probe:<name>:U`; the app evaluates them from the same series as the report slots. Run Solver is blocked when a criterion watches a removed part or probe.
  - Model (schema v6, extended in place on the unpublished task branch): `Reports.probes` (name: letter then letters, digits or _, at most 32; unique; location x y z), `Reports.slots` take any valid report id, `AsymptoticCriterion.quantity` any criterion quantity.
  - GUI: the Reports & Monitors node shows a Forces table (rows Cd, Cd,p, Cd,v, Cl, Cl,p, Cl,v, Cm, x_cp; columns All walls and each part; latest iteration, live), the mass balance rows and the y+ histogram (D-061); a Probes node adds (default name probeN, located one parts length behind the parts on their centre line), edits (name, "x y z") and removes probes.
- Alternatives considered: pressure/viscous coefficients from forceCoeffs' results (only in the solver log, not in its file); one probes object for all probes (its results are only the average, min and max over the probes, so a criterion could not watch one probe); summing the flux of every open boundary (zero on slip and symmetry patches).
- Consequences: real coarse-sphere run (300 iterations, 20 m/s, frontal A_ref 0.9977 m2): Cd 0.1721 = pressure 0.1604 + viscous 0.01165 (93 % pressure drag), mass imbalance 0 % at iteration 300 (inlet and outlet sum(phi) equal to the 7 written digits; at most 0.0083 % at iteration 2). Two-part run (Ball + Pod at 4 deg, 30 iterations): Ball 0.07346 + Pod 0.01790 = 0.09136; body-axis x_cp at iteration 30: Ball -0.0067 m, Pod 1.5047 m (each sphere's centre of pressure at its own centre, x = 0 and 1.5 m, as it must be for a sphere; the lift-normal alternative would put the Pod's 0.7 m away), all walls -0.343 m; the Ball's x_cp is undefined at iteration 5 only (F_z = 0.37 N = 6.7e-4 q A_ref while it changes sign). Probes: re-running the 300-iteration sphere with cellPoint gave byte-identical force, coefficient and mass-flow files and moved the probe values (front probe 0.5 m upstream on the stagnation line: p 42.72 -> 49.53 m2/s2, U 17.71 -> 17.28 m/s; p + |U|^2 / 2 = 198.9 against the free stream's 200). More files per run (a few kB per 100 iterations per object).

- Status: Accepted (review chat 2026-10-17, docs/QUESTIONS.md item 65). Revised in place on 2026-10-18: the points follow the connectivity of the cut and each loop is split at its min-x and max-x points (it was: ordered by x, split by the sign of n_z, one zig-zag line for z sections).

## D-063 Parallel solver runs: decomposePar, mpirun, reconstructPar; clean stop through mpirun
- Status: Accepted (review chat 2026-10-18, docs/QUESTIONS.md item 66: the low-Re steady comparison is the acceptance; serial / parallel agreement is defined only for converged cases, an oscillating case has no common answer). Was Proposed (Task 6.6, [NUMERICS-REVIEW]). The mpirun binding and the recommended core count are D-064.
- Context: runs were single-process (D-010, D-046); the machine has 12 physical cores. The viewer, the reports and ParaView must keep reading an ordinary case, and the clean stop and the stopping criteria must behave as in serial.
- Decision:
  - Model (schema v6, extended in place on the unpublished branch): `Solvers.cores` (int >= 1, default 1). The upper limit is the machine's physical cores, read at run time (foam/parallel.physical_cores: distinct (physical id, core id) pairs of /proc/cpuinfo, else os.cpu_count()), never stored: the Solvers node's "Cores (N physical)" spin box stops at N and Run Solver is disabled with "<n> cores requested; this machine has N physical cores." when a project asks for more. The cores are left out of the results hash (a parallel run solves the same case).
  - Case: with cores > 1 the solver files include system/decomposeParDict (numberOfSubdomains N, method scotch; keywords of decompositionMethod.C and scotchDecomp's TypeName, as the v2606 tutorials write it; scotch needs no coefficients). SolverRun then runs `decomposePar -force` (log.decomposePar), `mpirun -np N simpleFoam -parallel` through FoamRun with the clean stop (log.simpleFoam) and, whenever the solver exits with code 0 (iteration limit, criteria met, user's clean stop), `reconstructPar -latestTime` (log.reconstructPar; not stoppable, not run after a crash or a killed run). The decomposePar output and a summary ("Decomposed into 4 subdomains (scotch): 47575-48533 cells per processor (max 0.99% above average), 6396 faces between processors") go to the console, then "Reconstructed the latest time" or the reconstructPar failure. Clearing a run and a new mesh delete processor<N>/ (they hold a decomposed copy of the mesh), and a new run deletes the old decomposeParDict and logs. Checked on a real run: the master writes postProcessing/ in the case directory and the log (Info is master-only) in the serial format; the parsers read both unchanged.
  - Clean stop: verified empirically that Open MPI 4.1.6's mpirun forwards SIGUSR1 to the ranks: SIGUSR1 to mpirun (FoamRun's process; the shell is exec'ed) stopped the 4 ranks of the coarse sphere 1.04 s later, each wrote the current iteration, End, "Finalising parallel run", exit code 0, no process left. (v2606 Time::operator++ also reduces the stop flag over the ranks with maxOp, so one rank receiving the signal would be enough.) So parallel runs use the same SIGUSR1 stop as serial runs (D-010), including the app-side stopping criteria (D-058); the file-based stop was not needed.
  - Timeout and escalation: mpirun puts each rank in a process group of its own, inside FoamRun's session (start_new_session), so SIGTERM / SIGKILL go to the process group and to every live process of the session (foam/runner.signal_session, from /proc/<pid>/stat), and when the main process ends any process still alive in the session is killed (RunResult.orphans_killed).
- Alternatives considered: the file-based stop (controlDict stopAt writeNow with fileModificationSkew 0, measured earlier at about 0.01 s; not needed since mpirun forwards SIGUSR1); hierarchical or simple decomposition (needs the subdomain counts per direction); running the reconstructed case only on request (the viewer and reports would read processor directories); keeping the decomposed case after reconstruction (it stays until the next run or mesh, for ParaView's decomposed reader).
- Consequences: the coarse sphere (192220 cells) at Re = 200 (0.003 m/s, steady, converged), alpha 4 deg, 300 iterations: serial Cd 0.6420303, Cl -0.02335689 in 188.8 s; 4 cores Cd 0.6420300, Cl -0.0233531 in 94.5 s (dCd -4.7e-5 %, dCl -0.016 %, speedup 2.00). At 20 m/s the same sphere oscillates and never converges: after 100 iterations serial Cd 0.15672, Cl -0.05975 against 4 cores Cd 0.16280, Cl -0.08752 (3.9 % and 46 %); the paths separate from iteration 2 (Cd -3.3 %) because the linear solves stop at relTol 0.01 and their result depends on the partition, so only converged solutions are comparable (item 66); the windowed mean of Cd over iterations 51-100 agrees to 0.5 % (0.16789 against 0.16703). A clean stop at about iteration 8 on 4 cores leaves U and p of that iteration in every processor directory and, reconstructed, in the case directory; a 20 s timeout kills every rank. Each parallel run keeps a decomposed copy of the mesh and of the written fields in the processor directories (about the size of the mesh and fields again).

- Status: Proposed (review chat decision of 2026-10-18 asked for the study; numbers below)

## D-066 Mesh independence study with the Celik GCI (schema v7)
- Status: Proposed (Task 6.4, [NUMERICS-REVIEW]). D-065 was not used: the freestream far field of Part B was not applied (docs/QUESTIONS.md item 71).
- Context: PLAN 6.4: judge grid convergence of chosen reports on a family of systematically refined meshes with the Celik et al. (2008) procedure already used by the flat plate study (D-036), without touching the user's case.
- Decision:
  - GCI (foam/gci.py, no Qt; the flat plate study now imports it): Celik, Ghia, Roache, Freitas, Coleman, Raad, J. Fluids Eng. 130 (2008) 078001: apparent order p by fixed-point iteration of p = |ln|eps32/eps21| + q(p)| / ln r21 with q(p) = ln((r21^p - s) / (r32^p - s)), phi_ext^21, e_a^21, e_ext^21, GCI_fine^21 = 1.25 e_a^21 / (r21^p - 1), GCI_medium^32, and the asymptotic-range ratio GCI_medium^32 / (r21^p GCI_fine^21) (in range within 0.1 of 1). Oscillatory convergence (eps21 and eps32 of opposite sign) gets no number: "oscillatory, GCI not applicable". A p > 0 that does not reproduce the data (the change grows with refinement: phi = phi0 + C h^p requires eps32 / eps21 = r21^p (r32^p - 1) / (r21^p - 1)) is "divergent", equal solutions on two grids "undefined"; none of them gets a GCI. Tested against Table 1, first column, of the paper (p 1.534, phi_ext 6.1685, GCI_fine 2.175 %, GCI_medium 4.113 %; the third, oscillatory column gets no number), exact power laws with equal and unequal ratios, and the divergent and undefined cases.
  - Model (schema v7, migration v6 -> v7 adds the defaults): `Simulation.studies.mesh` = `MeshStudySettings`: `ratio` r in linear cell size (default sqrt(2), at least 1.3, at most 4), `current_as` "fine" (default; the study adds two coarser levels) or "medium" (one coarser, one finer), `quantities` (report ids of core/reports.py, default ["Cd"]), `cores` (MPI ranks of each level's run, default 1).
  - Levels (foam/mesh_study.py): linear size factors f = r^2, r, 1 (current = fine) or r, 1, 1/r (current = medium); a level divides the background cell budget by f^3 (or multiplies an explicit base size by f) and multiplies the target surface size by f, so the surface refinement levels, which follow log2(base / target surface size), stay the same and every cell scales by f; explicit level overrides (mesh and per part) are kept. Prism layers: the SAME absolute stack on every level, the first-layer thickness, expansion ratio and number of layers of the current settings (relative sizing: first = final_layer_thickness x surface cell size / ER^(n - 1) at the current maximum surface level; absolute y+ sizing: the y+ first layer and the current computed count), written with relativeSizes false (MeshCaseInput.fixed_layers; the quality controls keep following the project's sizing, so a relative-sized project gets no relaxed set). Reason: the flat plate study (D-036) showed Cf changing 2.6 % between first-cell y+ 1 and 0.5 and then converging; with relative layers the first-cell y+ would change between levels and mix a wall-resolution change into the grid error. The representative cell size is h = (V_domain / N_cells)^(1/3) from the cell count of each level's checkMesh report (not the estimate).
  - Before launching, the Mesh Study node shows per level the estimated cells (background cells x the cells per background cell of the current mesh record, or 1.9 without a mesh, marked "assumed") and the solver time up to the iteration limit from the last run's time per cell-iteration (the run record now stores `duration_s` and `cores`; ideal scaling with the cores assumed; "unknown" without a timed run), and the shared layer stack. A level above the 2,000,000 background-cell limit blocks the study with that reason.
  - Run (foam/mesh_study.StudyRun, gui/mesh_study.py, gui/study_control.py): every level is a marker-protected case <project>/case_study/level_<n>/ (meshing dictionaries, the part STLs and seed lines written before the run; case/ is never written); per level MeshRun, then the project's solver files with the study's cores, then SolverRun with the project's stopping criteria; the final value of every quantity is read from the postProcessing files. A level whose mesh is invalid stops the study ("failed"). A level that does not end with "criteria met" is kept and flagged; every GCI row then says "unreliable: <levels> did not meet the stopping criteria". Stop stops the running step cleanly and ends the study ("stopped"). One OpenFOAM job at a time: meshing, Run Solver and the study block each other with a reason.
  - Results: case_study/study.json (settings, per level cells, h, run state, iterations, time and values, status), a non-modal "Mesh study" window: a table per quantity (h and value per level, p, extrapolated value, GCI fine, asymptotic ratio with in / not in range, note), the levels table and a chart of the chosen quantity against h (QPainter; levels that did not meet their criteria hollow in the warning colour), and Export CSV (one row per quantity).
- Alternatives considered: scaling the surface refinement levels instead of the target size (levels are powers of 2: r = sqrt(2) cannot be represented); relative prism layers on each level (y+ changes with the level); the estimated instead of the actual cell counts for h; running the levels inside case/ (would destroy the user's mesh and results).
- Consequences: real study (tests/test_mesh_study.py, marker `long`, 293 s): the coarse sphere (24 x 24 STL, default domain and mesh as the fine level, r = sqrt(2)) at Re 200 (0.003 m/s), alpha 4 deg, 4 cores, Cd and Cl asymptotic (window 50, 1e-4), all levels met the criteria: coarse 36,995 cells, h 0.37400 m, Cd 0.665034, Cl -0.0274491 (337 iterations); medium 82,567 cells, h 0.28619 m, Cd 0.657493, Cl -0.0222605 (429); fine 192,220 cells, h 0.21593 m, Cd 0.643797, Cl -0.0235317 (449). Cd: "divergent" (the change grows with refinement, 0.0075 then 0.0137: these meshes are not in the asymptotic range), Cl: "oscillatory"; no GCI for either. The actual size ratios are 1.307 and 1.325, not 1.414: the background cells scale with r^3 but the surface and layer cells with about r^2 (docs/QUESTIONS.md item 72). Three meshes and runs cost about three times a normal run plus the meshing.

## D-071 Surface regions and patch assignment (schema v8)
- Status: Proposed (Task 3.1 introduced the model; Task 3.5 completed it). [NUMERICS-REVIEW] for the wall BC on every patch and the snappyHexMesh region entries.

- Decision:

A part whose only patch is its own name is written exactly as before (one STL, no `regions` entries; the inputs hash of a project without regions is unchanged, so existing meshes stay up to date). Any other part's STL in constant/triSurface has one ASCII `solid <patch>` per patch; its geometry entry gets `regions { <patch> { name <patch>; } }`, its refinementSurfaces entry `regions { <patch> { level (min max); patchInfo { type wall; inGroups (<part>Group); } } }` and every patch its own nSurfaceLayers entry. The lost-part guard checks every patch (MeshRun, the mesh study); the solver case gives every patch the wall BCs (U noSlip, p zeroGradient, k kqRWallFunction, omega omegaWallFunction, nut nutUSpaldingWallFunction), and the per-wall force objects, y+ and report lists are per patch. Triangles outside every region (not produced by any edit) fall on the part's first patch.

## D-078 The domain as an operation; bullet and C-type domain shapes
- Status: Accepted (owner review, 2026-10-18: farfield slip as for the box sides, the rounded surface resolved at the base size, the background box margin; docs/QUESTIONS.md item 80).
- Context: the far-field domain was always a box generated with the parts (D-019). The owner asked for rounded domains and for the domain to be an explicit operation.
- Decision:
  - Shapes (`Domain.shape`, schema v9 of D-077), in multiples of L (the largest extent of the union of the boxes of the parts the domain is sized around, `Domain.parts`, None = all; c = its centre): "box" as before; "bullet": a hemisphere of radius R = `radius` L centred at c and a cylinder of the same radius behind it, axis along +x through c, the outlet `downstream` L after the parts' rear (defaults 5 and 10); "c_type": in the x-z plane a half-disc of radius R centred at c in front, flat top and bottom at c_z +- R, a flat rear `downstream` L after the parts, flat spanwise sides at c_y +- `lateral` L (defaults 5, 10, 5). With symmetry "y_min" the bullet's axis lies in the plane y = the parts' y_min and only y >= that plane is kept; the C-type spans [y_min, y_min + `lateral` L] with the symmetry plane at y_min. `downstream` is measured from the parts' rear for every shape. A part outside the domain gets a warning.
  - Boundary roles: box as before; bullet: front hemisphere inlet, rear disc outlet, cylinder farfield; C-type: front inlet, rear outlet, top and bottom farfield, spanwise sides sides; symmetry when enabled. farfield gets the conditions of sides / top / bottom (slip, nut calculated; `physics_case.FAR_FIELD_BY_SHAPE`); no boundary condition changed.
  - geometry/domain_surface.py: the closed triangulated domain surface with a cell array `role` per triangle (every shape, the box as six faces), seams shared so it is watertight; 64 segments around the bullet, 16 per quarter circle, 8 on the rear radius (enclosed volume within 0.22 % of the analytic one).
  - Meshing a rounded shape: blockMesh makes a background box = the domain's bounds grown by `BACKGROUND_MARGIN_CELLS` (2) base cells, all faces in the patch "background"; with symmetry the box's y_min face lies exactly on the plane and is the symmetryPlane patch "symmetry" (exactly planar), and the domain surface written for snappyHexMesh (constant/triSurface/domain.stl, one solid per role) leaves the symmetry region out and continues its open edge 2 base cells through the plane. domain.stl is a refinement surface at level (0 0), its regions named after the roles become the patches (type patch), no layers, its feature edges at level 0; locationInMesh is halfway between the inlet on the axis and the parts' front, at the parts' y-z centre, in the background grid. After snappyHexMesh, `createPatch -overwrite` with no new patches removes the patches left without faces (the background patch). The guard (case/vortexcfd_domain.json: the expected domain patches and the background patches, written for every shape; `mesh_run.domain_problems`, `MeshReport.domain_errors`) marks the mesh invalid when a background patch still has faces or an expected domain patch has none; Run Solver is then disabled. The base size uses the actual domain volume: base = (V / background cell target)^(1/3); the cell counts and the 2,000,000 limit are those of the background box.
  - Operations: in the "Empty" analysis nothing is created automatically: the Fluid Domain node reads "Fluid Domain (not generated)" and holds "Generate domain..." (also Edit > Generate Domain... and a button in the node's properties): a dialog with the parts to size it around (the selected part, else all), the shape, its sizes and the symmetry, applied as one undoable step (enabled, shape, sizes, symmetry, parts). Meshing says "Generate the domain first" until then. In the "External flow" analysis the domain is generated on the first import with the preset's shape, as before. The Regions folder gains "Fluid Region (domain minus parts)": the domain, the subtracted parts and the locationInMesh that selects the kept side. Shape and every size are editable in the Fluid Domain properties (only the fields of the shape are shown; "Lateral" reads "Half-width" for the C-type), each edit one undoable step; the mesh inputs hash includes the domain, so any change marks the mesh out of date. The properties show the bounding box, the volume and the parts the domain is sized around.
  - Viewer: the domain surface as a translucent wireframe for every shape; selecting a boundary role highlights its faces.
- Alternatives considered: blockMesh with curved edges or an O-grid for the bullet (hard to keep general with symmetry and parts of any size); snapping the symmetry plane to the domain surface (a snapped symmetryPlane is not exactly planar); keeping the empty background patch with a boundary entry in the 0/ fields (the solver files would need an extra patch); a domain sized around the bounding sphere of the parts (changes L).
- Real coarse meshes (sphere of radius 0.5 m, 24 x 24, base size 0.5 m, surface levels 1-2, no layers, defaults otherwise; tests/test_domain_shapes.py, marker slow): box 1935.308 m3, 17,798 cells; bullet 1086.376 m3, 11,058 cells; C-type 1442.583 m3, 13,870 cells; checkMesh OK, every expected patch with faces and no background patch left in all three; 3.7 to 4.6 s each. With y_min symmetry: bullet 6,229 and C-type 7,635 cells, also OK. simpleFoam ran 3 iterations on the bullet and on the symmetric C-type mesh (exit code 0).
- Consequences: the reserved patch names gain farfield, background and domain (a part with such a name gets a suffix). Older cases without vortexcfd_domain.json pass the guard unchanged.

## D-082 Meshing benchmark: runner, metrics, result files and regression rules
- Status: Proposed (task 5.0, Part C).
- Context: the benchmark of D-081 needs one command that runs the cases through the app's own pipeline, measures the mesh and writes comparable result files, and a comparison that flags regressions. The meshing orchestration the app uses (`prepare_job`, `prepare_solver_case`, the CAD import) lives in the Qt-free modules gui/meshing.py, gui/solving.py and gui/part_ops.py, but importing any gui module imported Qt through gui/__init__.py.
- Decision:
  - Command: `.venv/bin/python -m vortexcfd.bench [--cases ...] [--compare <file>] [--no-solve] [--result <file>] [--out <folder>] [--generate]`. Each case runs in its own Python process (so the peak memory belongs to that case); a crash is recorded as a failed case. Project folders go to run/bench/<case>/ (an earlier one is removed only when it holds <case>.vcfd).
  - Pipeline: Project.create with the "External flow" preset, the geometry copied into <project>/geometry and added as File > Import does (`part_ops.cad_parts` for STEP), `meshing.readiness` / `prepare_job`, `MeshRun` (with the lost-part and domain guards) and its `MeshReport`. The only change to the generated case is output: `writeFlags ( layerFields );` is appended to system/snappyHexMeshDict so snappyHexMesh writes nSurfaceLayers, thickness and thicknessFraction on the wall patches. A second `checkMesh -writeAllSurfaceFields -writeFields (nonOrthoAngle) -constant -noZero` writes the face non-orthogonality field (the mesh is not changed; its time is not counted).
  - Quality, from the app's checkMesh log: max and average non-orthogonality, faces above 70 degrees (checkMesh's 70-90 degree "severely non-orthogonal" count plus its above-90 "errors"), max skewness and checkMesh's "highly skew" faces (above 4), max aspect ratio, failed checks and every "***" line by type. Faces above 65 and above 70 degrees are also counted from the face field (internal faces only).
  - Layers, per wall patch, for all walls and per zone, area-weighted from the layer fields: coverage = share of the area whose faces have the full target layer count; extruded = share with at least one layer; mean layers; mean achieved thickness (m) and its ratio to the wanted thickness (mean thicknessFraction). Patches and zones with coverage below 80 % are listed.
  - Cost: cells; snappyHexMesh's own stage times (castellation "Mesh refined in", snap, layers, whole run), the wall time of every meshing step, of the meshing run and of the case; peak memory = getrusage(RUSAGE_CHILDREN).ru_maxrss of the case's process after meshing and after the solver run, i.e. the largest single child process (snappyHexMesh or one solver rank), not the sum over MPI ranks.
  - Robustness: MeshReport.valid, the lost parts and the domain guard errors; surface fidelity = the distances from the unique points of the wall patches to the original surface (analytic for the sphere; a tessellation of the STEP at 1e-5 of its diagonal and 2 degrees otherwise), max and RMS divided by the case's reference length.
  - y+, labelled "indicative, not converged": `prepare_solver_case` with the app's default physics, 400 iterations, the stopping criteria removed, write interval 400 and the recommended cores (D-064); `SolverRun`; the yPlus field at the last time on the walls: min, area-weighted mean, max and the share of the wall area with y+ in [0.5, 2] times the target y+. 400 iterations keep the full benchmark near 10 minutes on the development PC.
  - Result files: benchmarks/results/<UTC date and time, YYYYMMDDTHHMMSSZ>_<short git sha, "-dirty" with uncommitted tracked changes>.json and a .md with the summary table and per-case details; git-ignored. The committed baseline is benchmarks/baseline.json (plus BASELINE.md).
  - `--compare <file>` prints per-case deltas and flags as regressions: wall or zone coverage down more than 2 points; max non-orthogonality up more than 2 degrees; more faces above 70 degrees; cells up more than 10 %; surface fidelity RMS worse by more than 10 %; a failed mesh, a lost part or a case missing from the new result. A total time up more than 25 % is only flagged. The exit code is 1 when there is a regression.
  - Tests: fast tests of the metric code on small fixtures (a captured failing checkMesh log, the existing sphere logs, a one-cell case with layer fields, distances to a sphere, the comparison rules); a real run carries the new marker `bench`, which is skipped unless selected (`pytest -m bench`) and excluded from scripts/ship.sh.
  - Layers (superseded in this point by D-083: the modules moved to workflow/, bench/ imports nothing from gui/ and gui/__init__.py imports MainWindow eagerly again): gui/__init__.py imports MainWindow and main on first access, so `import vortexcfd.gui.meshing` loads no Qt. The new package bench/ may import core, foam, geometry and, from gui/, only meshing, solving and part_ops; tests/test_layers.py enforces it, and a test checks that importing the benchmark loads neither PySide6 nor pyvistaqt.
- Alternatives considered: hand-written dictionaries (would not measure what the user gets); moving the Qt-free orchestration modules out of gui/ into a layer of their own (cleaner, but a larger move; docs/QUESTIONS.md); computing face non-orthogonality in Python from the polyMesh files (OpenFOAM's own cell centres are needed to match checkMesh); coverage as the share with any layer (reported as "extruded": it hides partly collapsed stacks, e.g. 99.5 % extruded but 1.5 of 3 layers at the wing's trailing edge in a development run); snappyHexMesh's final layer table only (one row per patch, no zones).
- Consequences: the numbers describe the meshes the app writes with its defaults. Time and memory depend on the machine and on its load; time is only flagged. A result made with a dirty tree says so in its name.

## D-093 Surface preparation: diagnostics, intersection features, CAD union (schema v11)
- Status: Proposed (task 5.2, Part C). [NUMERICS-REVIEW] for the sewing tolerance, the junction refinement level, the hidden-curve rule and the default strategy.
- Context: PLAN 5.2. A multi-component model whose components interpenetrate and are not sewn (the owner's untrimmed aircraft export: six compounds of loose faces, every overlapping pair crossing; benchmarks/RESULT_5.2_before.md) reached snappyHexMesh as separate surfaces with nothing at the junctions: no feature line where a wing enters the fuselage, and nothing in the app looked across parts (the self-intersection check is per part, the repair is per part and lost the wings on a one-part import).
- Decision:
  - Model (schema v11): `Simulation.surface_prep` (None = not run: the parts mesh as imported, as before) holds the operation's result: the strategy, the hash of the parts' geometry when it ran (`inputs_hash`), per Part a `PreparedPart` (the strategy applied to it, its prepared surface and region ids or None, a note when it fell back), the intersection-curve file (`features_file`), the report rows and the run time. v10 files migrate with nothing to fill (fixture tests/data/project_v10.json); presets hold no geometry, so a v10 preset reads as v11 unchanged.
  - Operation: Edit > Prepare Surfaces... (also the "Surface Preparation" node between the geometry and the continua, with "Prepare surfaces..." and "Remove" in its properties) asks the strategy and runs `workflow/surface_prep.prepare` on the geometry worker (D-073) over a snapshot; the result is applied with `Project.set_surface_prep` as one undoable step if the parts did not change meanwhile. Files are written under <project>/geometry/ with content-hashed names, so undo only points back; Save As copies them. The node shows the strategy, the state (up to date, or out of date), the per-part result and the report.
  - Meshing uses the result only while the parts' geometry still hashes to `inputs_hash` (`surface_prep.state`); an out-of-date result blocks meshing with "The surface preparation is out of date: the parts changed after it ran. Run Prepare Surfaces again, or remove it." It is a meshing input (the mesh hash includes the strategy and the files); without a preparation the hash is unchanged.
  - Diagnostics (geometry/surface_prep.py, on the parts' tessellations in metres, against the surface cell size of the mesh settings): per part whether it is closed (open and non-manifold edges) and, for CAD parts, whether its faces sew into a closed solid; the pairs of parts that cross each other with their intersection-curve length (and how much of it is on the outside of the other parts); gaps smaller than a cell (open boundary loops: the median distance from one loop to the nearest open edge of another, or a single loop's smaller in-plane extent; and pairs of parts closer than a cell without crossing, "touching" at 0); the share of a part's area thinner than a cell (rays along each sampled triangle's normal in both directions, VTK cell locator: thickness, or facing surfaces closer than a cell).
  - Intersection curves: computed on the tessellations snappyHexMesh sees, as the segments where triangles of different parts cross (geometry/intersections.intersection_segments: the self-intersection check's grid, then the overlap of each pair's plane cuts), instead of OpenFOAM's surfaceBooleanFeatures: no extra utility run per pair, the pairs come out for the diagnostics too, and it is tested without OpenFOAM. Segments whose middle lies inside a third part (generalised winding number above 0.5, robust to the small holes of these tessellations) are left out: they are not on the outer skin and, as snap features, would pull that part's surface inwards; pairs whose curves are shorter than 1e-6 of the diagonal only touch.
  - Strategy "intersection_features": the parts stay as they are; the curves are written as a featureEdgeMesh and added to snappyHexMesh's `features` (castellation and snapping, with `explicitFeatureSnap` as for every feature) at the junction level: the highest maximum surface level of the parts (their overrides, else the mesh's), so a junction is resolved like the finer of the two surfaces [NUMERICS-REVIEW]. The parts' insides are discarded by snappyHexMesh as before (locationInMesh is outside all parts).
  - Strategy "cad_union" (geometry/cad_union.py): each CAD part's faces are sewn (BRepBuilderAPI_Sewing) with a tolerance of 1e-5 of its model's bounding-box diagonal (0.145 mm on the 14.5 m aircraft; OpenCASCADE's own default is a fixed 1e-6 model units) [NUMERICS-REVIEW], every closed shell is made a solid and oriented (ShapeFix_Solid), all solids are fused in one BRepAlgoAPI_Fuse (one part at a time when that fails, so the failing part is named), and the union is tessellated with the parts' smallest deflections. Every face of the union keeps its source part and source CAD face through the sewing and fuse history (Modified / IsDeleted), so each part gets its share of the outer skin as its prepared surface (metres) with the source CAD face ids as region ids: patches, regions and per-part forces stay one per part; together the shares are closed (they share their boundary nodes). The shares' open boundaries are the junctions, which surfaceFeatureExtract already extracts as features (openEdges). A part that is not CAD, cannot be sewn closed (reason with the free-edge count), cannot be fused, or keeps no outside surface falls back to intersection features: its own surface, with the curves between it and every other surface (the union's shares included) as features.
  - Only the parts that cross another part take part in the union; a part that crosses nothing (every part of a one-part project) keeps its own surface, so the operation never changes single-component geometry (the meshing case of a prepared one-part project is byte-identical to the unprepared one, tests/test_surface_prep.py).
  - Default strategy (the one the dialog proposes): **CAD union**, proposed from the 5.2 comparison on the owner's aircraft (benchmarks/RESULT_5.2.md) [NUMERICS-REVIEW]: against the trimmed reference it is the only strategy that moves the junctions closer (reference -> mesh RMS at the wing, horizontal and vertical tail junctions 1.33 / 2.03 / 1.68 mm against 4.87 / 5.10 / 2.60 mm as imported and 5.17 / 3.06 / 2.19 mm with intersection features), it leaves 0.030 m2 of wall inside a component against 0.079-0.080 m2, and its largest mesh -> reference deviation is 18.4 mm against 28.7 and 40.5 mm. Intersection features measured within noise of no preparation. Its mesh (like the trimmed reference's) fails checkMesh at the benchmark's 24-layer stack with negative-volume cells on the wing surface away from the junctions; without the layer phase it fails only the skewness check the as-imported mesh also fails (a 5.4 matter). The owner accepts or changes it.
- Alternatives considered: OpenFOAM's surfaceBooleanFeatures per pair (a utility run per pair at mesh time; the same curves); replacing the Parts' files with the prepared ones (like Repair part: a deflection edit would silently drop the union, and the operation could not be removed); a shell wrapper (implicit-surface or envelope wrapping: not built; Part D says whether it is needed); one combined STL for the union (the per-part patches and forces would need regions).
- Consequences: the junctions get feature lines; a preparation must be re-run after any change to the parts' geometry (meshing says so). The report rows are plain text stored in the project.
